AI Test Automation Assistant
Instruction Guide

Workflow for automating a requirement end-to-end with AI-assisted test generation — for Azure DevOps and Jira

Before You Start

  • Confirm the Azure DevOps work item is ready for automation with a clear user story and acceptance criteria.
  • Ensure the Azure DevOps MCP connection is configured and the target project is accessible.
  • Verify test environment credentials are set in src/config/.env.dev and the application under test is reachable.
  • Treat AI-generated test cases and code as a first draft. A QA engineer or lead should review the output before it is merged or reported.

Step-by-Step Instructions

Flow A — Azure DevOps Work item → Test Cases (Child links) → Feature file → Locators → Page Object → Spec → Run → Work item comment

Step A1: Trigger the automation

  1. Open the Kiro session in the IDE and confirm the workspace is the test framework project.
  2. Enter the trigger phrase with the work item ID, for example: Automate work item 37.
  3. Confirm Kiro reads the work item and returns the extracted title, user story, and mandatory fields.

Tip: Start with a well-formed work item — a clear "As a / I want / So that" story and explicit acceptance criteria produce the most accurate test cases.

Step A2: Review the generated test cases and feature file

  1. Review the manual Test Cases Kiro creates and links as Children of the work item (happy path, validation, dependent-field, and end-to-end).
  2. Confirm each test case has clear steps and expected results.
  3. Open the generated Gherkin feature file under features/istm/ and check the scenarios and tags map to the acceptance criteria.

Tip: The test cases are a draft. Adjust, add, or reject any scenario that is not supported by the work item.

Step A3: Confirm live locator discovery

  1. Kiro logs into the application and navigates to the target form using the Playwright healer.
  2. It inspects each field (piercing Shadow DOM) and interacts with it to confirm the locator works.
  3. Verified locators are stored in the object repository under object-repository/pages/.

Tip: Locators are confirmed by real interaction, not guessing — this is what keeps the tests stable and self-healing.

Step A4: Review the Page Object and test spec

  1. Review the generated Page Object in pages/, built only from verified locators and extending the shared base page.
  2. Confirm it is registered in the fixtures and barrel export.
  3. Open the test spec in tests/smoke/ and check it follows the Arrange–Act–Assert pattern with correct traceability to the work item and test case IDs.

Tip: Good generated code reads like the team wrote it — consistent naming, one class per file, and no hard-coded waits.

Step A5: Run, heal, and confirm results

  1. Kiro runs the spec headed on Chromium (up to two attempts, healing locators if needed).
  2. Review the run output: passed / failed, duration, and the record created (for example, a generated record ID).
  3. Confirm the success message and generated ID appear on screen and no application errors are shown.
  4. Kiro posts a results comment back to the work item and attaches the evidence screenshot.

Tip: A run that exits without error is not enough — always confirm the on-screen confirmation and the generated ID before reporting a pass.

Flow B — Jira Jira ticket → Zephyr test cases (linked) → Feature file → Locators → Page Object → Spec → Run → Jira comment

The Jira flow follows the same end-to-end pipeline as Azure DevOps. The differences are the requirement source (a Jira ticket instead of a work item), test-case management (Zephyr Scale instead of linked child work items), and where results are posted (a Jira comment). Steps B3 to B5 are identical to the Azure DevOps flow because the application under test and the automation layer are the same.

Step B1: Trigger the automation

  1. Open the Kiro session and confirm the Jira (Atlassian) MCP connection is configured for the target project (for example, project key KD).
  2. Enter the trigger phrase with the ticket key, for example: Automate KD-7.
  3. Confirm Kiro reads the ticket and returns the summary, user story, and acceptance criteria.

Tip: As with Azure DevOps, a clear "As a / I want / So that" story and explicit acceptance criteria produce the most accurate test cases.

Step B2: Review the Zephyr test cases and feature file

  1. Review the STEP_BY_STEP test cases Kiro creates in Zephyr Scale and links back to the Jira ticket.
  2. Confirm each test case has a clear objective, steps, and expected results.
  3. Open the generated Gherkin feature file under features/istm/ and check the scenarios and tags map to the acceptance criteria and Zephyr test case keys.

Tip: The Zephyr test cases are a draft. Adjust, add, or reject any scenario that is not supported by the ticket.

Step B3: Confirm live locator discovery

  1. Kiro logs into the application and navigates to the target form using the Playwright healer.
  2. It inspects each field (piercing Shadow DOM) and interacts with it to confirm the locator works.
  3. Verified locators are stored in the object repository under object-repository/pages/ — shared across both flows.

Tip: Locator discovery is application-driven, so it works identically whether the requirement came from Jira or Azure DevOps.

Step B4: Review the Page Object and test spec

  1. Review the generated Page Object in pages/, built only from verified locators and extending the shared base page.
  2. Confirm it is registered in the fixtures and barrel export.
  3. Open the test spec in tests/smoke/ and check the traceability header references the Jira ticket and Zephyr test case keys.

Tip: The Page Object and spec are reused across flows — only the traceability references differ.

Step B5: Run, heal, and post results to Jira

  1. Kiro runs the spec headed on Chromium (up to two attempts, healing locators if needed).
  2. Review the run output: passed / failed, duration, and the record created.
  3. Confirm the success message and generated ID appear on screen and no application errors are shown.
  4. Kiro posts a structured results comment back to the Jira ticket and can update the Zephyr execution status.

Tip: Keep the automated and manual outcomes in sync — update the Zephyr status so the Jira ticket reflects the true test state.

Example Use Case — Azure DevOps

Scenario: A work item with a user story and acceptance criteria needs an automated test covering the happy-path flow, with full traceability back to Azure DevOps.

  • Trigger with Automate work item <ID> in Kiro.
  • Review the linked test cases and the generated feature file.
  • Confirm the locators discovered live on the target form.
  • Review the Page Object and Playwright spec.
  • Run the test and confirm the on-screen confirmation and generated record ID.
  • Confirm the PASS comment and evidence posted on the work item, and update the test case outcome.

Example Use Case — Jira

Scenario: A Jira ticket (for example, KD-7) needs an automated test with test cases managed in Zephyr Scale and results reported back to Jira.

  • Trigger with Automate KD-7 in Kiro.
  • Review the Zephyr test cases created and linked to the ticket, plus the generated feature file.
  • Confirm the locators discovered live on the target form.
  • Review the Page Object and Playwright spec (traceability points to the Jira ticket and Zephyr keys).
  • Run the test and confirm the on-screen confirmation and generated ID.
  • Confirm the structured comment posted on the Jira ticket, and update the Zephyr execution status.
